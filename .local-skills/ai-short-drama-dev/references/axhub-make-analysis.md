# Axhub-Make 工程框架分析

## 1. 分析目标

本文用于提炼 `lintendo/Axhub-Make` 的工程框架设计，并判断哪些部分适合迁移到 AI 短剧制作工具。

分析结论不意味着本项目要切换技术栈。本项目仍保持当前架构：

- 后端：FastAPI
- 前端：Next.js
- 数据库：PostgreSQL
- 数据迁移：Alembic

Axhub-Make 更适合作为“AI 驱动创作型工具”的工程组织参考，而不是直接作为技术栈模板照搬。

## 2. Axhub-Make 整体架构

Axhub-Make 的核心结构可以概括为：

```text
Axhub-Make
├── 管理服务
│   ├── 管理 API
│   ├── 项目注册表
│   ├── 项目 metadata
│   ├── 本地资源读写
│   └── AI/Agent 能力调度
├── 管理 UI
│   ├── 项目列表
│   ├── 配置管理
│   ├── 资源管理
│   └── AI 辅助入口
├── client 工作区
│   ├── 业务项目源码
│   ├── resources
│   ├── themes
│   ├── prototypes
│   └── agent rules/skills
└── 构建与发布脚本
```

它不是单纯的前端项目，也不是单纯的服务端项目，而是一个“本地创作管理平台”。管理服务负责协调本地项目、资源、AI 工具、导出和发布；client 工作区承载用户真正要创作和维护的内容。

## 3. 值得借鉴的工程模式

### 3.1 项目工作区隔离

Axhub-Make 把管理服务和用户项目工作区分开：

- 管理服务负责运行、配置、注册项目和提供 API。
- client 工作区保存用户项目内容、资源、规则和运行数据。

对本项目的启发：

- 短剧项目不应只是一条数据库记录。
- 每个短剧项目后续可以拥有独立的“项目工作区”概念。
- 项目工作区可用于保存导出的 Markdown、角色参考图、剧本版本、生成记录和素材引用。

建议本项目后续形成类似结构：

```text
workspace/projects/<project-id>
├── metadata.json
├── exports
├── assets
│   └── characters
├── generations
└── scripts
```

第一期可以先用数据库保存结构化数据，等人物示意图、Markdown 导出和生成历史稳定后，再补工作区目录。

### 3.2 项目 metadata 与注册表

Axhub-Make 有项目注册表和项目 metadata，用于描述项目身份、资源、能力、导航和写入目标。

对本项目的启发：

- `Project` 表只保存基础项目属性是不够的。
- 后续需要项目级 metadata，描述这个短剧项目当前有哪些创作产物、哪些素材、哪些 AI 生成任务、哪些模块已确认。
- metadata 可以先落在数据库字段或独立表中，后续再导出为文件。

建议本项目逐步沉淀：

- 项目基础信息：名称、创意、平台、题材、集数、时长。
- 项目创作状态：选题、故事大纲、人物、人物图、分集大纲、剧本的完成状态。
- 项目能力状态：文本模型是否可用、图片模型是否可用、导出是否可用。
- 项目资源索引：角色图、本地素材、导出文件路径。

### 3.3 资源目录约定

Axhub-Make 通过明确的资源目录组织项目资料、模板、主题、原型和媒体。

对本项目的启发：

- 短剧系统后续一定会产生大量资源：人物图、参考图、分镜图、视频片段、配音、字幕、导出文件。
- 如果早期没有资源目录约定，后期会出现素材难追踪、导出难复现、生成结果无法关联的问题。

建议本项目按资源类型建立清晰约定：

- `characters`：人物设定和人物示意图。
- `story`：故事大纲、剧情脉络、伏笔和情绪曲线。
- `episodes`：分集大纲。
- `scripts`：单集剧本。
- `exports`：Markdown 或后续视频平台发布包。
- `generation-history`：AI 生成任务、提示词、模型、输入输出和错误。

### 3.4 能力开关与可用性状态

Axhub-Make 会根据项目 metadata、服务配置和运行环境判断某些能力是否可用。

对本项目的启发：

- 不应只在用户点击生成时才发现配置不可用。
- 页面应提前展示关键能力状态，例如文本模型未配置、图片模型未测试、项目时长超限、人物图未确认。

建议本项目后续增加项目级能力状态：

```text
文本生成：可用 / 未配置 / 测试失败
图片生成：可用 / 未配置 / 测试失败
故事大纲：未生成 / 已生成 / 已确认
人物示意图：待生成 / 待确认 / 已确认
导出：可用 / 缺少必要内容
```

这能让工作台从“表单集合”升级为“流程型创作工具”。

### 3.5 前端 API service 层

Axhub-Make 前端有集中式 API service，前端页面通过 service 调用后端接口，而不是在页面里散落 fetch 逻辑。

本项目已经有 `apps/web/lib/api.ts`，方向正确。

后续建议继续保持：

- 页面不直接拼接复杂接口。
- API 错误统一转换为中文提示。
- 复杂请求和响应类型集中定义。
- 对 AI 生成任务增加统一的 `generation` API 封装。

### 3.6 AI 生成历史记录

Axhub-Make 对 AI 图片生成有历史记录、任务状态、输入提示词、参考素材、输出图片和清理机制。

对本项目非常重要。

短剧系统后续需要复现和追踪 AI 生成结果，尤其是：

- 选题策划为什么这样生成。
- 故事大纲使用了哪个输入版本。
- 人物示意图由哪个提示词生成。
- 用户确认的是哪一版图片。
- 后续视频生成引用了哪个角色参考图。

建议本项目把 AI 生成任务作为一等数据对象，而不是只保存最终结果。

最小可行字段：

- 任务类型：故事大纲、人物设定、人物图、分集大纲、剧本。
- 输入快照：用户输入、上游内容版本、参考素材。
- 模型配置：模型类型、供应商、模型名称。
- 提示词：系统提示词、用户提示词或最终组合提示词。
- 输出结果：文本、图片路径或错误信息。
- 状态：等待中、生成中、成功、失败。
- 时间：创建时间、完成时间。

### 3.7 Agent rules 与 skills

Axhub-Make 在 client 工作区中放置 agent 工作规则和 skills，用于指导 AI 编程或 AI 创作流程。

本项目已经有两类 skill：

- `.local-skills/`：本地开发辅助，不同步 GitHub。
- `skills/`：用户侧短剧创作能力，需要同步 GitHub。

Axhub-Make 的启发是：只放 skill 还不够，复杂创作流程还需要 rules。

建议本项目后续考虑：

```text
skills/
└── short-drama-creator/

rules/
├── story-outline-rule.md
├── character-design-rule.md
├── episode-outline-rule.md
└── script-writing-rule.md
```

其中 skill 用于定义“什么时候使用能力”，rules 用于定义“具体如何产出高质量内容”。

### 3.8 分组测试命令

Axhub-Make 的测试命令按场景分组，例如服务端 API、运行时、导出、客户端等。

对本项目的启发：

- 当前项目还处于早期，简单命令足够。
- 后续功能变多后，应按模块拆分验证命令，避免每次都跑全量测试。

建议后续逐步形成：

```text
npm run check:web
npm run check:api
npm run test:api:projects
npm run test:api:model-configs
npm run test:api:generation
npm run test:web:workbench
```

## 4. 对 AI 短剧项目的落地建议

### 4.1 短期适合落地

第一期内适合优先吸收：

- 保持前端 API service 层集中管理。
- 在文档中明确项目工作区和资源目录的长期方向。
- 为人物示意图设计生成历史和确认状态。
- 为模型配置增加可用性状态展示。
- 在工作台页面展示流程状态，而不是只提供独立表单。

### 4.2 中期适合落地

进入“故事大纲、人物、分集大纲、剧本”完整链路后，建议落地：

- `GenerationTask` 数据对象。
- 创作产物版本管理。
- 项目级 metadata 或状态汇总接口。
- 用户侧 rules 目录。
- Markdown 导出时携带资源引用和生成版本信息。

### 4.3 长期适合落地

进入图片、分镜、视频生成阶段后，建议落地：

- 项目工作区文件目录。
- 素材资产管理。
- 生成任务队列。
- 失败重试和生成历史清理。
- 角色一致性参考素材的版本锁定。
- 项目导出包。

## 5. 不建议照搬的部分

### 5.1 不切换到 Node server + Vite 架构

Axhub-Make 使用 Node server 和 Vite 多入口构建。本项目已经采用 FastAPI + Next.js + PostgreSQL，这更适合当前目标：

- FastAPI 适合后续扩展 AI 服务、任务队列和文件处理。
- PostgreSQL 适合保存结构化创作数据和生成历史。
- Next.js 适合构建完整 Web 工作台。

不建议为了参考 Axhub-Make 而替换当前技术栈。

### 5.2 不引入复杂 vendor 同步机制

Axhub-Make 有 vendor 包同步和本地打包需求，这是它独立发布形态带来的复杂度。

本项目当前不需要：

- 本地 vendor 包管理。
- 多运行时打包。
- 内置第三方复杂编辑器包。

### 5.3 不提前引入原型/画布能力

Axhub-Make 有大量原型、画布、设计稿和导出能力。这些能力和短剧制作方向有部分相似，但不是第一期核心。

本项目第一期应聚焦：

- 项目创建。
- 模型配置。
- 故事大纲。
- 人物设定。
- 人物示意图。
- 分集大纲。
- 单集剧本。
- Markdown 导出。

画布、分镜图、视频生成应放在后续阶段。

### 5.4 不过早引入大量 UI/Agent 集成

Axhub-Make 集成了较多 UI 库、Agent 入口、IDE 打开能力和发布能力。当前项目不应过早引入这些复杂能力。

建议原则：

- 先完成稳定创作闭环。
- 再补素材、版本、导出和自动化。
- 最后再考虑多 Agent、多模型、多发布平台。

## 6. 推荐演进路线

结合 Axhub-Make 的经验，本项目可以按以下顺序演进：

1. 完成当前第一期 PRD 的核心闭环。
2. 增加 AI 生成任务记录，先覆盖故事大纲、人物设定和人物示意图。
3. 增加项目工作台状态汇总，让用户知道下一步该做什么。
4. 增加项目资源目录约定，优先覆盖人物示意图和 Markdown 导出。
5. 拆分用户侧 rules，让短剧创作质量不只依赖单个 skill。
6. 引入版本管理和导出包，为后续视频生成做准备。

## 7. 结论

Axhub-Make 最值得借鉴的不是具体技术栈，而是它对“AI 创作工具”的工程抽象：

- 管理服务和用户项目解耦。
- 用户产物有明确资源目录和 metadata。
- AI 生成过程可追踪、可复现、可清理。
- Agent 工作流有 rules 和 skills 承载。
- 前端通过集中 API service 与后端能力对接。
- 功能可用性通过能力状态提前暴露给用户。

这些模式与 AI 短剧制作工具高度相关，尤其适合指导本项目从“生成几个文本结果”升级为“可持续维护的短剧创作工作台”。
