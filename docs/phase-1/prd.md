# 第一期 PRD：短剧故事策划、人物确认与剧本工作台

## 1. 文档信息

- 产品名称：AI 短剧创作工作台
- 阶段名称：第一期，短剧故事策划、人物确认与剧本工作台
- 文档版本：v0.2
- 文档状态：草案
- 目标用户：个人短剧创作者
- 核心目标：帮助创作者从一个短剧想法出发，生成可编辑、可保存、可导出的短剧策划资料、整体故事大纲、人物设定、人物示意图、分集大纲和单集剧本。

## 2. 背景

本项目的长期目标是帮助个人创作者独立完成短剧内容生产，并将作品发布到线上平台。

完整短剧制作链路包括选题、整体故事设计、人物设定、人物形象确认、分集大纲、剧本、分镜、素材、配音、字幕、剪辑和发布。第一期不追求完成整个链路，而是优先解决最前置、最影响后续质量的部分：短剧故事策划、人物确认与剧本生成。

第一期完成后，创作者应能够把一个模糊的短剧想法，转化为一套结构化项目资料，包括选题方案、整体故事大纲与剧情脉络、人物设定、人物示意图、分集大纲和至少一集完整剧本，并将这些内容导出为 Markdown 文件。

## 3. 问题定义

个人创作者在制作短剧时，通常会遇到以下问题：

- 有题材想法，但难以快速判断故事卖点是否清晰。
- 不知道如何设计适合短剧的强钩子、强冲突和反转。
- 缺少整体故事脉络，容易只写出单集桥段，而不是一部完整短剧。
- 短剧集数和单集时长缺少约束，容易导致整体体量失控。
- 人物设定容易单薄，人物关系和秘密不够支撑多集剧情。
- 缺少角色视觉参考，后续进入 AI 视频生成时容易出现人物不一致。
- 分集结构难以规划，容易出现节奏拖沓或中途断裂。
- 剧本创作耗时长，且不容易符合短视频平台的节奏。
- 创作资料分散在不同文档中，不方便继续修改、复用和导出。

第一期要解决的核心问题是：

> 如何让个人创作者快速完成一部短剧从创意到可打磨剧本、可确认人物形象的前期生产闭环。

## 4. 产品目标

### 4.1 业务目标

- 帮助创作者在较短时间内完成一个短剧项目的策划草稿。
- 降低短剧前期创作门槛，让非专业编剧也能开始搭建故事。
- 在剧本生成前先沉淀整体故事脉络，减少后续剧情跑偏。
- 在人物生成后提供示意图，方便创作者确认角色形象，并为后续视频生成提供一致性参考。
- 为后续分镜、配音、字幕、视觉素材和发布流程打基础。

### 4.2 用户目标

- 用户可以创建一个短剧项目并记录基础信息。
- 用户可以手动调整短剧集数、单集时长和总时长。
- 用户可以从一个想法生成多个可选的短剧方向。
- 用户可以生成整体故事大纲与剧情脉络。
- 用户可以生成清晰的人物设定和人物关系。
- 用户可以为主要人物生成示意图并确认角色形象。
- 用户可以生成完整分集大纲。
- 用户可以生成至少一集完整剧本。
- 用户可以对生成内容进行人工编辑和重新生成。
- 用户可以导出项目文本资料和人物示意图引用。

### 4.3 成功指标

- 用户可以在 10 分钟内生成一个短剧项目草稿。
- 用户可以从创意输入完成到整体故事大纲、人物设定、人物示意图和至少一集剧本生成。
- 用户会对 AI 生成内容进行修改或重新生成，而不是只查看结果。
- 用户可以确认至少 1 个主要人物的示意图。
- 用户可以导出 Markdown 文件用于后续创作或备份。
- 用户愿意基于第一期工具继续制作真实短剧项目。

## 5. 用户画像

### 5.1 核心用户：个人短剧创作者

用户特点：

- 希望自己制作短剧并发布到线上平台。
- 可能具备短视频经验，但未必具备专业编剧能力。
- 更关心能否快速产出内容，而不是复杂团队协作。
- 愿意使用 AI 作为创作助手，但希望保留最终修改权。
- 计划后续使用 AI 图片或 AI 视频工具制作素材，因此需要较早确认角色视觉形象。

核心诉求：

- 快速把想法变成故事。
- 快速获得整体故事脉络、分集大纲和单集剧本。
- 能够控制短剧长度和单集时长。
- 能够确认主要人物的视觉方向。
- 能够反复调整内容方向。
- 输出结果能直接进入后续分镜和制作流程。

## 6. 使用场景

### 6.1 从零开始创建短剧项目

用户只有一个模糊想法，例如“都市逆袭爽剧，女主被丈夫背叛后发现自己是豪门继承人”。用户希望系统帮助其扩展为完整短剧项目。

### 6.2 控制短剧整体体量

用户希望手动调整短剧集数和每集时长，但系统需要确保单集不超过 2 分钟，总时长不超过 240 分钟，避免后续制作规模失控。

### 6.3 快速生成多个选题方向

用户不确定哪个故事方向更适合发布，希望系统围绕同一题材生成多个剧名、卖点、冲突和爽点方向，方便选择。

### 6.4 复用已有世界观和角色卡

用户已经沉淀了一套世界观或几个常用角色，希望可以在多个短剧项目中复用，而不是每次从零重新输入。用户可以先在资产库中维护世界观和角色卡，再选择加载到具体项目中。

加载到项目后的世界观和角色卡应成为项目内可编辑副本。用户在项目中修改这些内容时，不应直接修改资产库原始内容。

### 6.5 生成整体故事大纲与剧情脉络

用户希望系统先搭建整部短剧的故事骨架，包括故事背景、主线目标、核心矛盾、阶段性反转、情绪曲线、伏笔和结局方向，再继续生成人物与分集。

### 6.6 生成角色和人物关系

用户希望系统自动设计主角、反派、配角、人物目标、人物秘密和人物关系，为后续剧情提供支撑。

### 6.7 生成人物示意图

用户希望在文字人物设定后看到角色示意图，用于确认人物年龄、气质、服装、发型、脸部特征和整体风格，并作为后续视频生成的人物一致性参考素材。

### 6.8 规划完整分集大纲

用户希望系统根据选题、整体故事大纲和人物设定，生成完整分集结构，每集都有钩子、冲突、反转和悬念。

### 6.9 生成并改写单集剧本

用户希望系统基于某一集大纲生成完整剧本，并支持继续改写，例如增强冲突、缩短对白、提高爽感或改成更口语化。

### 6.10 导出项目文本

用户希望把当前项目内容导出为 Markdown 文件，用于后续编辑、备份或交给其他工具继续处理。

```text
进入系统

 -> 创建或选择角色卡资产
 -> 创建项目
```

## 9. 功能需求

### 9.1 模型 API 配置与连通性测试

用户可以配置自己的文本生成模型 API 和图片生成模型 API。配置中心应以“用户自定义配置”为核心，不绑定单一供应商；系统可以提供常用供应商预设，帮助用户减少重复填写。配置完成后，用户可以点击手动测试按钮，系统通过实际调用接口判断接口是否通畅可用。

配置类型包括：

- 文本生成模型 API：用于选题策划、整体故事大纲、人物设定、分集大纲、单集剧本和改写等文本生成任务。
- 图片生成模型 API：用于人物示意图、角色三视图等图片生成任务。

文本生成模型配置字段包括：

- 供应商名称。
- API Base URL。
- API Key。
- 模型名称。
- 可选备注。

图片生成模型配置字段包括：

- 配置方式：供应商预设或自定义配置。
- 供应商名称。
- 供应商预设，可选，例如火山方舟 Seedream。
- API Base URL。
- API Key。
- 模型名称。
- 图片尺寸。
- 是否支持参考图输入。
- 可选备注。

图片生成模型供应商预设要求：

- 第一期可内置火山方舟 Seedream 作为图片模型预设之一，但不能把系统设计成只支持火山方舟。
- 选择火山方舟 Seedream 预设时，系统可自动带出默认 API Base URL：`https://ark.cn-beijing.volces.com/api/v3`。
- 选择预设后，用户仍可根据实际开通的模型填写或修改模型名称、图片尺寸和备注。
- 用户可以选择自定义供应商，手动填写 API Base URL、模型名称、图片尺寸和能力说明。
- 后续应允许继续扩展阿里百炼、腾讯混元、OpenAI-compatible、SiliconFlow 等图片模型预设，而不影响角色卡生成流程。

连通性测试要求：

- 用户可以分别测试文本生成模型和图片生成模型。
- 文本模型测试应发送一个轻量测试请求，并判断是否返回可用文本。
- 图片模型测试应发送一个轻量测试请求，并判断是否返回图片 URL、图片文件或可解析的图片结果。
- 如果图片模型声明支持参考图输入，系统应在角色三视图生成时允许结合角色文字设定和已上传参考图。
- 测试成功后，系统记录最近测试时间和测试状态。
- 测试失败时，系统展示失败原因，例如 API Key 错误、模型不存在、网络不可达、响应格式异常或额度不足。
- 未完成可用配置时，系统应阻止对应类型的生成任务。

安全要求：

- API Key 不应在普通页面中明文展示。
- 用户编辑 API Key 时，可以重新输入并覆盖旧值。
- 导出 Markdown 时不包含 API Key。

默认决策：

- 第一期支持单用户配置，不做多用户配置隔离。
- 文本模型和图片模型独立配置、独立测试。
- 至少各支持一组当前启用配置。
- 图片模型第一期支持供应商预设和自定义配置两种方式。
- 火山方舟 Seedream 只是第一批图片模型预设之一，自定义配置始终保留。

验收标准：

- 用户可以保存文本生成模型配置。
- 用户可以保存图片生成模型配置。
- 用户可以手动测试文本模型接口。
- 用户可以手动测试图片模型接口。
- 用户可以通过火山方舟 Seedream 预设快速创建图片模型配置。
- 用户可以通过自定义配置接入其他图片模型供应商。
- 测试成功后，系统显示可用状态和最近测试时间。
- 测试失败后，系统显示明确错误信息。
- 未配置文本模型或测试不可用时，系统不允许执行文本生成任务。
- 未配置图片模型或测试不可用时，系统不允许生成人物示意图或角色三视图。
- API Key 不会出现在 Markdown 导出内容中。

### 9.2 创作资产库

用户可以在项目外独立管理可复用的世界观和角色卡，并在创建项目或进入项目工作台后选择加载。

资产类型包括：

- 世界观资产：用于保存题材、时代背景、世界规则、组织、地点、阶层、禁忌、整体风格等长期设定。
- 世界观条目：用于拆分世界观中的地点、组织、人物关系背景、关键规则、历史事件等可被生成任务引用的内容。
- 角色卡资产：用于保存可复用人物设定，包括姓名、身份、背景、目标、秘密、人物关系、说话方式、视觉描述和示意图引用。

加载规则：

- 世界观和角色卡可以被多个项目选择使用。
- 加载到项目时，系统生成项目内快照副本，保留原始资产 ID、原始版本和加载时间。
- 项目后续生成故事大纲、人物设定、分集大纲和剧本时，只读取项目内快照副本，不直接读取资产库原始内容。
- 项目未加载任何世界观或角色卡时，仍可按原流程从创意开始生成。

编辑规则：

- 编辑资产库原始世界观或角色卡，不自动影响已加载到项目中的副本。
- 编辑项目内世界观或角色卡副本，不影响资产库原始内容。
- 当原始资产有新版本时，项目可以提示来源已更新，但是否同步由用户手动决定。
- 用户可以将项目内修改后的世界观或角色卡另存为新的资产库资产。

交互要求：

- 用户可以创建、编辑、查看和停用世界观资产。
- 用户可以创建、编辑、查看和停用角色卡资产。
- 用户可以在项目创建或项目工作台中选择已有世界观和角色卡。
- 用户可以查看当前项目已加载的世界观和角色卡。
- 用户可以编辑项目内快照副本。
- 用户可以移除项目中已加载但未继续使用的快照副本。

验收标准：

- 同一个世界观资产可以被多个项目加载。
- 同一个角色卡资产可以被多个项目加载。
- 项目内修改不会回写资产库原始内容。
- 资产库原始内容更新不会自动覆盖项目内副本。
- 后续生成任务应优先引用项目内已加载的世界观和角色卡副本。

### 9.3 项目创建与时长配置

用户可以创建一个新的短剧项目，并配置短剧长度。

项目基础字段包括：

- 项目名称。
- 创意描述。
- 目标平台。
- 题材类型。
- 集数。
- 单集时长。
- 总时长。
- 目标受众。
- 内容风格。
- 备注。

时长规则：

- `episode_count` 表示集数，必须为正整数。
- `episode_duration` 表示单集时长，单位为分钟，必须大于 0 且不超过 2。
- `total_duration = episode_count * episode_duration`。
- `total_duration` 必须大于 0 且不超过 240 分钟。
- 当单集时长超过 2 分钟，或总时长超过 240 分钟时，系统必须阻止保存和后续生成。
- 超限时系统应提示用户修改集数或单集时长。

默认决策：

- 第一期仅支持本地或单用户项目，不做多用户协作。
- 项目名称可以由用户手动输入，也可以根据创意自动生成。
- 目标平台可先支持通用文本输入，后续再做枚举选项。
- 如果用户未填写集数，默认生成 20 集。
- 如果用户未填写单集时长，默认 1 分钟。

验收标准：

- 用户可以创建项目。
- 用户可以查看已创建项目。
- 用户可以编辑项目基础信息。
- 项目内容刷新页面后不丢失。
- 输入 121 集、每集 2 分钟时，系统阻止保存，因为总时长为 242 分钟。
- 输入每集 2.5 分钟时，系统阻止保存，因为单集超过 2 分钟。
- 输入 120 集、每集 2 分钟时，系统允许保存，因为总时长为 240 分钟。

### 9.4 创意输入

用户可以输入一段自然语言描述，说明想做什么类型的短剧。

输入示例：

```text
我想做一部都市逆袭爽剧，女主被丈夫背叛后发现自己是豪门继承人，共 20 集，每集 1 分钟，适合抖音。
```

系统应基于创意描述提取或推断：

- 题材。
- 主线冲突。
- 目标平台。
- 可能的受众。
- 情绪基调。
- 主要卖点。
- 建议集数和单集时长。

验收标准：

- 用户可以保存创意描述。
- 系统可以基于创意描述生成后续内容。
- 用户可以修改创意描述并重新生成后续内容。
- 从创意中推断出的集数和单集时长仍必须满足项目时长规则。

### 9.5 选题策划生成

系统根据项目基础信息和创意描述生成选题策划。

输出内容包括：

- 剧名候选，建议 5 个。
- 一句话故事。
- 故事卖点。
- 目标用户画像。
- 核心冲突。
- 核心爽点或情绪点。
- 前 3 秒开头钩子建议。
- 整体风格建议。
- 风险提示，例如题材俗套、冲突不够强、集数支撑不足等。

交互要求：

- 用户可以选择一个剧名作为项目名称。
- 用户可以编辑选题策划内容。
- 用户可以重新生成完整选题策划。
- 用户可以针对某一部分单独改写。

验收标准：

- 系统可以生成结构化选题策划。
- 用户可以编辑并保存结果。
- 用户可以基于选题策划继续生成整体故事大纲与剧情脉络。

### 9.6 整体故事大纲与剧情脉络生成

系统根据项目基础信息、创意描述、选题策划，以及项目内已加载的世界观和角色卡快照，生成整部短剧的故事骨架。

输出内容包括：

- 故事背景。
- 主线目标。
- 核心矛盾。
- 故事起点。
- 起承转合结构。
- 阶段性反转。
- 情绪曲线。
- 关键伏笔。
- 结局方向。
- 整体节奏建议。
- 与当前集数和总时长匹配的剧情容量建议。

交互要求：

- 用户可以编辑整体故事大纲。
- 用户可以重新生成完整故事大纲。
- 用户可以局部改写故事背景、主线目标、反转、伏笔或结局方向。
- 用户确认后的整体故事大纲应作为后续人物设定、分集大纲和单集剧本生成的核心上下文。

验收标准：

- 系统可以生成独立的整体故事大纲与剧情脉络。
- 如果项目已加载世界观或角色卡，故事大纲应优先遵循项目内快照内容。
- 用户修改整体故事大纲后，后续人物设定、分集大纲和剧本生成应基于最新大纲。
- 整体故事大纲必须在生成人物设定之前生成或由用户手动填写。

### 9.7 人物设定生成

系统根据选题策划、整体故事大纲和项目内已加载的角色卡快照生成人物设定。

输出内容包括：

- 主角设定。
- 反派设定。
- 重要配角设定。
- 人物背景。
- 人物性格。
- 人物目标。
- 人物秘密。
- 人物关系。
- 人物情感弧线。
- 人物在剧情中的功能。
- 人物视觉描述。
- 形象关键词。

默认建议：

- 第一期至少生成 1 名主角、1 名主要反派、2 到 4 名配角。
- 人物关系先用文本列表表达，不做可视化关系图。
- 主要人物都应包含可用于生成示意图的视觉描述和形象关键词。

交互要求：

- 用户可以编辑人物信息。
- 用户可以新增、删除人物。
- 用户可以重新生成全部人物设定。
- 用户可以单独改写某个人物。
- 用户确认人物文字设定后，可以为该人物生成示意图。

验收标准：

- 系统可以生成完整人物设定。
- 如果项目已加载角色卡，人物设定应优先保留项目内角色卡快照中的核心身份、目标、关系和视觉描述。
- 人物设定可被后续人物示意图、分集大纲和剧本引用。
- 用户修改人物后，后续生成内容应尽量遵循最新人物设定。

### 9.8 人物示意图生成

系统根据人物文字设定、人物视觉描述和形象关键词，为主要人物生成示意图。

输出内容包括：

- 人物图片生成提示词。
- 人物示意图。
- 图片地址或本地路径。
- 图片生成版本。
- 用户确认状态。

示意图应辅助确认：

- 年龄感。
- 气质。
- 服装。
- 发型。
- 脸部特征。
- 角色风格。
- 与人物设定的一致性。

交互要求：

- 用户可以为单个人物生成示意图。
- 用户可以重新生成单个人物示意图。
- 用户可以确认当前示意图作为该人物的参考形象。
- 重新生成某个人物示意图时，不应覆盖其他人物图片。
- 已确认的人物示意图应作为后续视频生成的人物一致性参考素材。

验收标准：

- 生成人物设定后，系统可以为主要人物生成示意图。
- 用户可以确认或重新生成某个人物示意图。
- 用户确认人物示意图后，该图片应在导出内容中作为人物参考信息出现。
- 人物示意图生成不代表第一期支持完整视频生成。

### 9.9 分集大纲生成

系统根据选题策划、整体故事大纲和人物设定生成完整分集大纲。

每集输出内容包括：

- 集数编号。
- 本集标题。
- 开头钩子。
- 主要剧情。
- 主要冲突。
- 关键反转。
- 结尾悬念。
- 出场人物。
- 本集作用。
- 预计时长。

默认决策：

- 第一期支持用户在时长规则内自由设置集数。
- 如果用户未填写集数，默认生成 20 集。
- 单集时长默认 1 分钟，且不能超过 2 分钟。

交互要求：

- 用户可以编辑每集大纲。
- 用户可以重新生成全部大纲。
- 用户可以单独改写某一集。
- 用户可以基于某一集生成完整剧本。

验收标准：

- 系统可以按照指定集数生成完整大纲。
- 每集都包含钩子、冲突、反转和悬念。
- 分集大纲应遵循整体故事大纲与最新人物设定。
- 用户可以选择任意一集进入剧本生成。

### 9.10 单集剧本生成

系统根据项目基础信息、选题策划、整体故事大纲、人物设定和某一集大纲生成单集剧本。

剧本内容包括：

- 集数标题。
- 场景编号。
- 场景地点。
- 场景时间。
- 出场人物。
- 动作描写。
- 人物对白。
- 情绪提示。
- 结尾悬念。
- 预计时长。

剧本格式建议：

```text
第 1 集：标题

场景 1：地点 / 时间
出场人物：角色 A、角色 B

动作：
...

对白：
角色 A：...
角色 B：...
```

交互要求：

- 用户可以编辑剧本正文。
- 用户可以重新生成整集剧本。
- 用户可以按改写方向重写剧本。
- 支持的改写方向包括：更爽、更虐、更悬疑、更口语化、更短视频化、压缩时长、增强结尾悬念。

验收标准：

- 系统可以生成完整单集剧本。
- 剧本与当前整体故事大纲、人物设定和分集大纲保持一致。
- 剧本预计时长不应超过项目设置的单集时长。
- 用户可以编辑并保存剧本。
- 用户可以对剧本进行至少一种方向的改写。

### 9.11 内容编辑与版本控制

第一期需要支持基础编辑能力，保证用户可以修改 AI 结果。

功能要求：

- 选题策划、整体故事大纲、人物设定、人物示意图、分集大纲、单集剧本均可保存当前状态。
- 文本内容应支持人工编辑。
- 编辑后的内容应作为后续生成的最新上下文。
- AI 重新生成前应提示可能覆盖当前内容，或提供新版本结果。

默认决策：

- 第一期可以先实现简单版本记录，不做复杂 diff 对比。
- 每次生成或改写可以保存为一个历史版本。
- 用户可以查看最近若干次生成结果。

验收标准：

- 用户编辑内容后不会被意外丢失。
- 用户可以区分当前版本和新生成版本。
- 后续生成优先使用当前已确认版本。

### 9.12 Markdown 导出

用户可以将当前项目内容导出为 Markdown 文件。

导出内容包括：

- 项目基础信息。
- 集数、单集时长和总时长。
- 项目内加载的世界观快照及来源说明。
- 项目内加载的角色卡快照及来源说明。
- 选题策划。
- 整体故事大纲与剧情脉络。
- 人物设定。
- 人物示意图引用。
- 分集大纲。
- 已生成的单集剧本。

导出文件命名建议：

```text
项目名称-短剧策划与剧本.md
```

验收标准：

- 用户可以导出 Markdown。
- 导出的 Markdown 结构清晰。
- 导出内容与当前项目内容一致。
- 导出文件可以被普通 Markdown 编辑器打开。
- 已确认人物示意图应以图片地址、本地路径或引用说明的方式出现在导出内容中。

## 10. 非功能需求

### 10.1 可用性

- 第一版界面应以清晰、实用、低干扰为主。
- 用户应能明确知道当前处于哪个创作阶段。
- 每个生成动作都应有清晰入口和结果展示。
- 项目时长超限时，应明确提示是单集时长超限还是总时长超限。

### 10.2 可控性

- AI 生成内容必须允许人工编辑。
- 关键内容被覆盖前应有保护机制。
- 用户应能按模块重新生成，而不是每次从头开始。
- 人物示意图应允许单人单独重新生成，避免影响其他人物。

### 10.3 一致性

- 整体故事大纲、人物设定、分集大纲和剧本之间应尽量保持一致。
- 后续生成应基于用户确认过的最新内容。
- 已确认人物示意图应作为后续视觉资产生成的人物参考。

### 10.4 可扩展性

- 第一期的数据结构应为第二期分镜、第三期配音字幕、第四期视频生成预留扩展空间。
- 剧本、人物、大纲、人物图片等内容应尽量结构化保存。

### 10.5 内容安全

- 系统应避免主动生成明显违法、侵权或高风险内容。
- 对可能涉及敏感题材、抄袭风险或平台审核风险的内容，应提供提示。
- 人物示意图生成应避免生成侵犯真实人物肖像权或明显模仿特定现实人物的内容。

## 13. 用户故事

1. 作为个人短剧创作者，我想创建一个短剧项目，以便集中管理这个项目的所有创作资料。
2. 作为个人短剧创作者，我想输入一个自然语言创意，以便系统理解我想创作的故事方向。
3. 作为个人短剧创作者，我想配置目标平台和集数，以便生成内容更符合发布场景。
4. 作为个人短剧创作者，我想配置单集时长，以便控制每集短剧的内容密度。
5. 作为个人短剧创作者，我想看到总时长，以便判断整部短剧的制作规模。
6. 作为个人短剧创作者，我想在时长超限时被阻止保存，以便避免项目规模失控。
7. 作为个人短剧创作者，我想生成多个剧名候选，以便选择更适合传播的标题。
8. 作为个人短剧创作者，我想生成一句话故事，以便快速判断故事是否清晰。
9. 作为个人短剧创作者，我想生成故事卖点，以便明确这个短剧为什么值得看。
10. 作为个人短剧创作者，我想生成目标用户画像，以便判断内容是否匹配观众。
11. 作为个人短剧创作者，我想生成核心冲突，以便故事有足够的戏剧张力。
12. 作为个人短剧创作者，我想生成开头钩子，以便短剧前几秒能抓住观众。

## 14. 实现决策

- 第一期以单用户本地项目或单用户工作台为核心，不做账号体系。
- 第一期主数据库确定为 PostgreSQL，本地开发通过 Docker Compose 启动。
- 第一期包含模型 API 配置能力，支持用户配置自己的文本生成模型和图片生成模型。
- 图片模型配置以多供应商可扩展为目标，支持供应商预设和自定义配置。
- 火山方舟 Seedream 可作为第一批图片模型预设，但系统不能依赖单一供应商。
- 第一期纳入创作资产库设计，支持世界观和角色卡在项目外独立管理并被项目复用。
- 文本模型和图片模型独立配置、独立测试、独立启用。
- 文本生成任务依赖可用的文本模型配置，人物示意图生成依赖可用的图片模型配置。
- API Key 不进入 Markdown 导出，不在普通页面明文展示。
- 第一版以文本生产、人物示意图生成和编辑为主，不接入视频、配音和字幕生成。
- 整体故事大纲是独立模块，不合并进选题策划。
- 整体故事大纲位于人物设定之前，后续人物、分集和剧本生成都应引用它。
- 世界观和角色卡加载到项目后采用快照副本模型，不采用实时共享引用模型。
- 项目内快照优先于资产库原文参与生成；资产库原文更新不自动覆盖项目快照。
- 单集时长超过 2 分钟或总时长超过 240 分钟时，采用强校验：阻止保存和生成。
- 人物设定后支持生成主要人物示意图。
- 人物示意图优先服务角色确认和后续视频一致性参考，不要求做到专业角色一致性训练。
- 所有 AI 生成文本结果都必须可编辑。
- 后续生成应优先使用用户确认后的最新内容。
- 数据应尽量结构化，避免只保存一整段不可解析文本。
- Markdown 导出作为第一期唯一必须支持的导出格式。
- 版本记录先做轻量历史，不做复杂协同编辑和差异对比。
- 分镜、配音、字幕、视频生成相关字段可预留，但不进入第一期核心功能。

## 15. 测试与验收

### 15.1 测试原则

- 测试用户可见行为，不测试模型内部实现。
- 测试数据保存、编辑、重新生成和导出是否可靠。
- 测试核心流程能否从项目创建走到人物示意图确认、剧本生成和导出。
- 测试时长强校验是否可靠。

### 15.2 核心验收路径

1. 用户创建一个新项目。
2. 用户配置文本生成模型 API 并测试成功。
3. 用户配置图片生成模型 API 并测试成功。
4. 用户创建或选择一个世界观资产。
5. 用户创建或选择一个角色卡资产。
6. 用户输入短剧创意、集数和单集时长。
7. 系统校验总时长和单集时长。
8. 用户将世界观和角色卡加载到项目中。
9. 用户编辑项目内世界观和角色卡副本。
10. 用户生成选题策划。
11. 用户编辑并保存选题策划。
12. 用户生成整体故事大纲与剧情脉络。
13. 用户编辑并保存整体故事大纲。
14. 用户生成人物设定。
15. 用户编辑某个人物。
16. 用户为主要人物生成示意图。
17. 用户确认某个人物示意图。
18. 用户生成完整分集大纲。
19. 用户选择第 1 集生成剧本。
20. 用户对剧本执行一次改写。
21. 用户导出 Markdown 文件。

### 15.3 关键验收标准

- 输入 121 集、每集 2 分钟时，系统阻止保存。
- 输入每集 2.5 分钟时，系统阻止保存。
- 输入 120 集、每集 2 分钟时，系统允许保存。
- 未配置或未测试通过文本模型时，系统阻止文本生成任务。
- 未配置或未测试通过图片模型时，系统阻止人物示意图生成任务。
- 文本模型测试成功后，系统显示可用状态和最近测试时间。
- 图片模型测试失败后，系统展示可理解的失败原因。
- Markdown 导出不包含 API Key。
- 项目内容刷新后不丢失。
- 同一个世界观资产加载到多个项目后，项目内修改互不影响。
- 同一个角色卡资产加载到多个项目后，项目内修改互不影响。
- 修改项目内世界观或角色卡副本时，资产库原始内容不变。
- 修改资产库原始内容时，已加载项目不会被自动覆盖。
- 修改后的整体故事大纲能被后续人物、分集和剧本生成引用。
- 项目已加载世界观和角色卡时，整体故事大纲、人物设定、分集大纲和剧本生成应优先引用项目内快照。
- 重新生成不会无提示覆盖用户已编辑内容。
- 生成人物设定后，系统能为主要人物生成示意图。
- 重新生成某个人物示意图时，不覆盖其他人物图片。
- 用户确认人物示意图后，该图片在导出内容中作为人物参考信息出现。
- 导出的 Markdown 内容完整且结构清晰。
- 单集剧本与整体故事大纲、人物设定和分集大纲保持基本一致。

## 16. 不做范围

第一期明确不做：

- AI 视频生成。
- 场景图生成。
- 分镜图生成。
- 分镜拆解。
- 配音生成。
- 字幕文件生成。
- 在线剪辑。
- 自动发布到平台。
- 团队协作。
- 用户账号和权限。
- 支付系统。
- 数据分析看板。
- 移动端专门适配。

说明：

- 第一期支持人物示意图生成，但不支持场景图、分镜图或完整视频生成。

## 17. 风险与待确认问题

### 17.1 风险

- AI 生成内容可能套路化，需要通过提示词和改写能力优化。
- 长剧集一致性可能不足，需要确保后续生成引用最新整体故事大纲和人物设定。
- 人物示意图可能与文字设定不完全一致，需要支持重新生成和人工确认。
- 用户可能希望第一期就生成视频，需要通过产品定位控制预期。
- 如果数据结构设计过于松散，第二期分镜会比较难接。
- 图片生成能力会引入额外成本和生成耗时，需要在后续技术方案中控制调用频率和缓存。

### 17.2 待确认问题

- 第一版是否只做本地应用，还是直接做 Web 应用。
- 第一版是否提供常见模型供应商的配置模板。
- 第一版 API Key 是否需要系统级加密存储。
- 第一版目标平台是否优先围绕抖音短剧节奏设计。
- 是否需要在第一期加入内容合规提示。

## 18. 后续阶段衔接

第一期输出应为第二期分镜与制作资料工作台、第四期 AI 视觉资产与视频生成接入提供结构化输入。

第二期将基于第一期的单集剧本继续拆解：

```text
单集剧本 -> 场景 -> 镜头 -> 分镜描述 -> AI 图像/视频提示词 -> 制作清单
```

第四期将基于第一期确认的人物示意图继续扩展：

```text
人物设定 -> 人物示意图 -> 人物一致性参考 -> 镜头级视觉素材生成 -> 视频生成
```

因此，第一期在保存剧本时，应尽量保留场景、角色、动作、对白等结构；在保存人物时，应保留文字设定、视觉描述、图片提示词和已确认示意图引用，避免后续只能从纯文本重新解析。
