# 编码规范

## 1. 目标

本规范用于约束本项目后续前后端实现代码的可读性和可维护性。

核心原则：

- 代码命名应清晰表达职责。
- 注释应解释业务意图、边界条件和非显然逻辑。
- 不用注释重复代码已经能直接表达的信息。

本项目当前处于快速搭建阶段，但后续会持续扩展世界观库、角色卡库、项目工作台、AI 生成任务、人物示意图和导出能力。如果关键规则缺少注释，后续维护成本会快速上升。

## 2. 注释语言

- 默认使用中文注释。
- 技术名词可以保留英文，例如 FastAPI、Pydantic、SQLAlchemy、React state、API Key。
- 注释应简短直接，优先说明“为什么这样做”和“这里保护什么规则”。

## 3. 必须加注释的情况

### 3.1 业务规则

涉及产品约束、强校验和流程边界时必须注释。

示例：

- 单集时长不能超过 2 分钟。
- 总时长不能超过 240 分钟。
- 角色卡加载到项目后生成快照，不回写原始角色卡。
- 世界观加载到项目后生成快照，不自动同步资产库新版本。

### 3.2 跨字段校验

当校验依赖多个字段或有计算字段时，需要说明校验意图。

示例：

- `total_duration = episode_count * episode_duration`。
- 只有 `active` 角色卡可以加载到项目。
- 已归档资产仍保留历史项目来源追踪。

### 3.3 安全与隐私边界

涉及密钥、导出、响应脱敏和本地持久化时必须注释。

示例：

- API Key 不明文返回前端。
- API Key 不进入 Markdown 导出。
- 前端不得把 API Key 放入 URL、localStorage 或普通文本展示。

### 3.4 状态流转

复杂状态或用户可见状态切换需要注释。

示例：

- 保存中、测试中、成功、失败状态之间的互斥关系。
- 生成任务的前置条件。
- 项目内容被重新生成前的覆盖保护。

### 3.5 生成上下文规则

AI 生成相关上下文选择和优先级必须注释。

示例：

- 临时生成要求优先于项目内已确认内容。
- 项目内世界观和角色卡快照优先于资产库原文。
- 人物示意图生成优先使用项目内角色快照的视觉描述。

### 3.6 数据库与迁移约束

表结构、索引、版本字段、历史保留策略和迁移兼容逻辑需要注释。

示例：

- 版本号用于判断项目快照是否落后于来源资产。
- 归档替代硬删除是为了保留历史项目引用。
- 外键存在但不级联删除的原因。

## 4. 不建议加注释的情况

以下注释会降低代码质量，应避免：

- 逐行解释语法。
- 重复变量名、函数名已经表达的含义。
- 描述显而易见的 JSX 结构。
- 用注释弥补模糊命名。
- 大段容易过期的实现说明。
- 与代码实际行为不一致的历史注释。

不推荐：

```python
# 返回项目
return project
```

推荐：

```python
# 项目时长是后续生成流程的强约束，超限时必须在保存前阻断。
```

## 5. 后端注释要求

适用范围：

- FastAPI 路由。
- Pydantic schema。
- SQLAlchemy 模型。
- service 层业务逻辑。
- Alembic migration。

要求：

- 路由层只在说明接口边界、权限或安全策略时加注释。
- schema 中的字段校验和跨字段规则需要注释。
- service 层中的业务规则、状态流转和外部 API 调用保护需要注释。
- 数据库模型中非显然字段、版本字段、状态字段和关系字段需要注释。
- migration 中的兼容策略、默认值和不可逆操作需要注释。

## 6. 前端注释要求

适用范围：

- Next.js 页面。
- React 组件。
- 表单校验。
- API 调用封装。
- 状态管理。

要求：

- 复杂 React state 或多个状态互斥时需要注释。
- 表单校验与后端业务规则一致时需要注释。
- API 请求中涉及脱敏、安全或错误映射时需要注释。
- 用户可见状态切换复杂时需要注释。
- 明显 JSX 布局不需要注释，优先通过组件命名和结构表达。

## 7. 完成前自检

每次修改 `apps/api` 或 `apps/web` 后，完成前必须检查：

- 是否有关键业务规则没有注释。
- 是否有安全边界没有注释。
- 是否有复杂状态流转没有注释。
- 是否有生成上下文优先级没有注释。
- 是否存在无意义注释或已经过期的注释。

检查目标不是增加注释数量，而是确保后来维护代码的人能理解关键决策。
